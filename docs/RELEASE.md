# AnchorShell Release Policy

## 1. Canonical source

GitHub repository and GitHub Actions are canonical.

Do not distribute a local developer build as an official AnchorShell release.

## 2. Branches

Keep branch policy simple.

```text
main
feat/*
fix/*
```

Use short-lived branches.

## 3. Versioning

Semantic Versioning.

Pre-stable:

```text
v0.1.0-alpha.1
v0.1.0-alpha.2
v0.1.0-beta.1
v0.9.0-rc.1
```

Stable:

```text
v1.0.0
```

## 4. Required GitHub Actions

### CI

Runs on pull request and push to `main`.

Required jobs once G1 source exists:

- frontend install/build
- TypeScript check
- Rust fmt/check/test
- Windows Tauri build smoke

### Release

Triggered by a version tag.

Required outputs:

- Windows x64 installer
- SHA256 checksum
- build metadata containing commit SHA
- GitHub Release attachment

Before G8, installers may be unsigned and must be clearly identified as such.

## 5. Release evidence

A release is valid only when:

- tag points to intended commit
- required CI is green
- release workflow is green
- artifact is generated by GitHub Actions
- checksum matches uploaded artifact
- gate acceptance evidence is recorded

## 6. No false PASS

Do not mark a runtime acceptance item PASS from:

- code review
- static compilation
- unit tests alone
- mocked behavior

Physical/runtime acceptance must be labeled separately.

## 7. Rollback

Keep previous GitHub Release assets available.

Auto-update, when introduced, must have failure handling before it becomes the default update path.
